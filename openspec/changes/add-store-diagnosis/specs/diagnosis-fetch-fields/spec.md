## ADDED Requirements

### Requirement: 取数名称只冻结展示名
两级取数与需求 §6.3 的名称冻结只覆盖展示名、检查单分组和维度值。JSON 键、文件路径、比率量纲（含 0–1 与 0–100）和 SQL 列都未冻结。实现 MUST NOT 把本规格中的展示名写成已经冻结的键名、路径、量纲或列名。kickoff 与领域基线里引用的指标名只标记为参考、非 SQL 列契约。

本规格不修改 `diagnosis-symptom-pipeline` 的「环比计算口径」「恶化方向与下滑分档」和「指标可取数性」。黄标五条原文仍以「指标可取数性」为准。

#### Scenario: 存储契约仍未冻结
- **WHEN** 实现按本规格取数
- **THEN** 展示名可以核对，但规格没有给出 JSON 键、快照路径、比率量纲或 SQL 列，实现不得把展示名当成已冻结的列契约

### Requirement: 需求 6.3 四类异常下钻
需求文档 §6.3 的四类异常下钻与汇总已冻结。触发项用词以需求正文为准，MUST NOT 改写：

1. 店铺绩效异常。范围是商品评价、物流履约、客户服务、店铺运营等 10 项二级子指标的明细下钻与汇总。
2. 非买家责任退款退货率。范围是该指标的明细下钻与汇总。
3. 延迟发货（48小时发货）。范围是该指标的明细下钻与汇总。
4. 延迟到货。范围是该指标的明细下钻与汇总。

需求截图没有逐项写出这 10 个二级名字。领域基线的指标白名单有 10 个名字，只作为参考、非 SQL 列契约，不得改写上面四条需求用词，也不得写成列契约：用户评价分、非买家责任退货退款率、延迟发货率、延迟到货率、缺货率、24小时回复率、售后准时率、爆旺款率、售罄健康分、活动报名率。kickoff 表格把其中一项写作「24 小时回复率」，并另有「店铺绩效分」作为可下钻到这 10 项的绩效分；这些同样只是参考、非 SQL 列契约。

检查单截图在店铺绩效下只展开 8 个叶子，用词与需求 6.3 和参考白名单都不同。本规格同时保留检查单叶子原文和需求触发项原文，不把它们合并成同一 JSON 键或 SQL 列。缺货率、活动报名率没有出现在检查单截图叶子里。

#### Scenario: 四类下钻使用需求用词

- **THEN** 四个触发项是店铺绩效异常、非买家责任退款退货率、延迟发货（48小时发货）、延迟到货

#### Scenario: 需求用词不被检查单改写

- **THEN** 需求触发项仍写作「非买家责任退款退货率」和「延迟发货（48小时发货）」，两边都不改名，也不冻结为同一列

### Requirement: 黄标五条不随本轮截图增减
`fetchable=false` 的黄标仍是这五条原文，一条不多、一条不少：库存、推广 roas、流量异常（建议调价未调价）、流量异常SPU数占比、推广 Roas。第二级截图没有把库存标黄时，库存仍属于这五条。截图标黄不新增第六条黄标，也不替换这五条的写法。

检查单截图另有写法「推广roas」「流量异常SPU数/占比」「推广Roas」。这些是检查单展示名，不替换黄标原文，也不在本规格里冻结成同一个 JSON 键。单独的「流量异常」仍然不是黄标。

「推广花费（关停）」和「roas环比变化」保持可取数，不标 `fetchable=false`。检查单叶子「超预算(关停)」不是第六条黄标。本规格不把「超预算(关停)」与「推广花费（关停）」冻结为同一 JSON 键或 SQL 列。

#### Scenario: 库存未标黄仍不可取数
- **WHEN** 第二级截图的商品检查单列出库存但没有标黄
- **THEN** 库存仍是五条黄标之一，`fetchable=false`，症状管线 SKIP，不产生数值

#### Scenario: 关停花费与环比变化保持可取数
- **WHEN** 症状引擎遇到推广花费（关停）或 roas环比变化
- **THEN** 二者都不是 `fetchable=false`，也不因父节点推广 roas 标黄而被 SKIP

#### Scenario: 截图写法不改黄标原文
- **WHEN** 检查单出现推广roas、流量异常SPU数/占比或推广Roas
- **THEN** 黄标清单仍是库存、推广 roas、流量异常（建议调价未调价）、流量异常SPU数占比、推广 Roas，不增不减，也不改字
